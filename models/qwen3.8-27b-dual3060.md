# Qwen3.8-27B (ISTA GSQ-RCO 3-bit, MTP) on the dual-RTX-3060 box

**Model:** Qwen3.8-27B — dense ~27.3B, hybrid SSM + full attention (17 of 66 layers), native MTP head
**Quant:** ISTA DASLab [GSQ-RCO](https://huggingface.co/ISTA-DASLab/Qwen3.8-27B-GSQ-RCO-GGUF) **IQ3_S-mtp (3.0-3.4 bpw)**, 12.1 GB, with the release's own BF16 mmproj projector (0.93 GB; served on CPU)
**Hardware:** the secondary GPU server — Intel i5-7400 (4C/4T — no hyperthreading), 32 GB DDR4, two RTX 3060 12 GB (one on a CPU x16 slot at Gen3 x16; one on a chipset PCIEX4_1 slot **measured negotiating Gen3 ×1 on 2026-11-18** — historical width across the November boot: unverified, probably ×1 (one continuous boot; a link can retrain without a reboot); the ribbon-riser card sits in PCIEX1_1 next to the CPU, which per the manual does not share lanes with this slot, so the ×1 is not by design; the November reports’ x4 wording is retracted, see Provenance), PHB, **no P2P**
**Runtime:** llama.cpp **b12383** (stock), `--split-mode layer`; MTP via `--spec-type draft-mtp` (shared-weight head; f16 draft KV, 1.02 GiB at 256K/2)
**Status:** ✅ **Fallback (boot-resident card default since 2026-11-15)** — the fleet's 27B primary is the [dual-3090 vLLM endpoint](qwen3.8-27b-rtx3090.md); this box serves when that one is unavailable. The 35B brain and the 27B cannot co-reside, so this endpoint is cold-startable in ~13 s when swapped in.

## Current production config (P1, since 2026-11-16)

The **P1 profile of the max-context campaign is the production default** (adopted 2026-11-16 after a canary of P2 found a concurrent-stream regression; P2 was tried as the default for one afternoon and reverted). `--ctx-size 262144 --parallel 2`, **A8 layout** (`CUDA_VISIBLE_DEVICES=1,0` GPU-order flip + `--tensor-split 60,40` + `--mmproj-device none`), q4_0/q4_0 KV, MTP on (default n-max 5), `-b 256 -ub 128 -t 4`, `--jinja --load-mode none`, non-unified KV. Idle VRAM 9934/10899 MiB (headroom 1978/1012); the pre-campaign 1,1 launcher is preserved for a full restoration. P2 (unified 200K/slot + `--cache-prompt --cache-reuse 4096`, ub 256, n-max 2) stays a documented candidate: it gave 1.6-2.1 s turns on a 182K conversation while pool-resident, but (a) two concurrent long prefills do not stream in real time (~225 s first byte on the second, burst delivery, one early close — attribution between `-ub 256` / `n-max 2` / per-slot cap still open) and (b) the 2026-11-17 context-hierarchy run found that in b12383 the RAM prompt cache cannot restore evicted states beyond the ~150 MiB checkpoint class, so a 182K turn is fast only while its state stays in the unified pool. The 2026-11-18 matched window ([report](../reports/2026-11-18-dual3060-27b-matched-p1-vs-unified.md), with a same-day addendum correcting the decode cells as non-comparable and tightening the PCIe/dmon wording) tested the unified pool as the *only* changed flag (P1 verbatim vs P1 + `--kv-unified --kv-unified-per-slot 262144`): cold prefill indistinguishable at 11.8K/23.6K/47.2K and prefix reuse identical in both — no prefill/reuse benefit found, **P1 confirmed as the production default**. The hub machine polls this box's PCIe link every 5 minutes (an independent `llm-hub-pciewatch` service, not a hub module): negotiated width **and generation** from both nvidia-smi and lspci (cross-checked, mismatches alert), device and upstream-port capability, with a de-duplicated alert log and an append-only time series. The evening of 2026-11-18, five minutes after the M3 window closed and the 22:48:50 production reload finished, both 3060 links dropped **Gen3→Gen1 with no kernel AER or retrain events** (bracketed measurements: Gen3 at 21:53 and 22:49:02, Gen1 from 22:54 onward) — an unattributed driver-side re-init; the box is therefore serving at Gen1 ×1 today (compute-bound inference unaffected; cold loads and the prefill bandwidth ceiling at a quarter of the Gen3 figure), and every future window's per-cell sampler must record the generation, not just the width. The 0.3–0.9 GB/s dmon bursts of 2026-11-15 come from an era whose generation is unverified.

## Context-persistence findings (2026-11-17)

Full measurements: [2026-11-17-dual3060-27b-context-hierarchy-ram-disk](../reports/2026-11-17-dual3060-27b-context-hierarchy-ram-disk.md). The GPU→RAM→disk hierarchy, as it actually behaves in b12383:

- **RAM tier** (`--cache-ram` + `--cache-idle-slots`): the server's *internal, automatic* prompt cache (idle-slot states parked in a bounded LRU RAM store, reloaded on the next request for that slot; the path of upstream issue #30961). It saves idle prompt states (16K≈1.35 GB, 87K≈2.0 GB, 171K≈3.8 GB, 182K≈4.1 GB incl. MTP draft state) but **restores only the ≤~150 MiB checkpoint class in 2-3 s; full-state loads of 1.8-3.3 GB fail** (`failed to restore kv cache`) under both 4096 and 8192 MiB budgets. No cross-session contamination observed. There is no *externally controlled* RAM snapshot API in this build; the file tier below is the only one operators can drive.
- **Disk tier** (`--slot-save-path`, `POST /slots/{id}?action=save|restore|erase`): works end to end and is **durable and correct** — 16K (1.12 GB, 0.9 s restore) and 128K (4.19 GB, 4.5-11 s) snapshots round-trip, **survive a full server restart, and survive a 27B→35B→27B model switch** on the same cards (post-switch follow-up: exact planted code after a 531 s cold re-prefill; see the correction below for why that run is clean). The 2026-11-18 isolation cells resolved the one open anomaly into a **size-dependent** behavior: with a 16K-class state (≈1.1 GB), erase→restore→followup reuses the full prefix (3.7–12 s, exact code, MTP on or off, explicit slot targeting verified in the engine log); with the 167K state (≈4.2 GB) the restored prompt-cache entry is evicted by the followup's allocation ("making room … removing oldest") and the return costs a full re-prefill (618 s). Slot routing was tested and is not the cause (automatic routing in this build is LCP-similarity based). **Net: disk = durable and correct at every tested size; fast return demonstrated up to the 16K-class, full re-prefill at 167K-class until the cache-retention behavior is fixed upstream.**
- Practical consequence: long-conversation persistence on this build is a **disk-snapshot story, not a RAM story**; the RAM cache is a small-prefix accelerator that is on by default (8192 MiB) and costs nothing to leave on. The practical multi-conversation shape: one large live conversation (167K fixture demonstrated; 182K+30K ceiling shown in the max-context campaign) plus small concurrent ones; a second large conversation parks on disk and pays a re-prefill on return.

## Max-context campaign (2026-11-15/16) — the Pareto set

Full measurements and method: [2026-11-15-dual3060-27b-maxctx-multi-consumer](../reports/2026-11-15-dual3060-27b-maxctx-multi-consumer.md). The three deployable profiles (adopting any is a two-line launch-script change; production was restored to the pre-campaign config after the campaign and stays there until the owner adopts one):

| profile | aggregate / per-session | the measured difference |
|---|---|---|
| **P1 Balanced multi-consumer** | 256K / 131K, 2 slots | GPU-order flip + 60,40 split + CPU projector → **1978/1012 MiB headroom on both cards** (was 1539/40) with no measurable decode penalty (24.8 → 24.8 t/s @16K); MTP n-max 2 (not 3) measured +14% decode (27.2 vs 23.8, acceptance 0.57 vs 0.37); `-ub 256` marginally the best prefill |
| **P2 Max context, flexible** | 256K unified, **per-session cap 200K** | `--kv-unified --kv-unified-per-slot 200000 --cache-prompt --cache-reuse 4096`: a 182K session plus a concurrent 30K session work with clean isolation; **conversation turns on the 182K session cost 1.6-2.1 s of prefill instead of 725-761 s** (99.97% cached); headroom 1704/874 |
| **P3 Largest stable aggregate** | **288K / 144K**, 2 slots | 128K-class retrieval verified; ~280 MiB post-deep headroom on the x4 card. 320K/2 boots but dies on its first prefill (`CUDA error: the resource allocation failed`) — the measured ceiling |

Negative results that closed levers: the MTP draft KV cannot be moved (`--spec-draft-device` is a measured byte-identical no-op for the built-in MTP; tensor override moves only ~40 MiB of head) and cannot be quantized (q8_0/q5_1/q4_0 draft KV OOMs at 256K and is dominated by f16 at 229K: +244 MiB, −4.5% decode). Slot count is not a memory lever in this build (the ctx size is the aggregate pool), and 4-way concurrent decode is plain time-slicing (~4.5 t/s per client vs 24 solo).
