# Qwen3.6-35B-A3B on Dual RTX 3060 12GB — Full Optimization, MTP, 256K, Vision

**Date:** 2026-08-27
**Category:** Model deployment
**Hardware:** 2× RTX 3060 12 GB (PCIe gen4, x4 + x8 links, one host bridge, no NVLink), AMD Ryzen 5 5600X 6c/12t, 30 GB RAM — Ubuntu 24.04 LXC (host RAM changed to 64 GB — 2×32 DDR4-2933 SO-DIMM via adapters — on 2026-08-26, the campaign day; the LXC's 30 GB limit and all-GPU config are unaffected)
**Stack:** llama.cpp `925e1179` (ggml-org mainline, 2026-08-26), CUDA 12.0, driver 580.95.05, `GGML_CUDA_FA_ALL_QUANTS=ON`

## Summary

Qwen3.6-35B-A3B (a 35B-parameter MoE, 3B active) runs at production quality on **two 12 GB consumer cards** — no NVLink, no 24 GB cards, ~$400 of GPU. The model (18.2 GB, MTP variant of Unsloth's IQ4_XS) fits fully in the 24 GB aggregate VRAM, and the right configuration gets there:

| Metric | Before (layer split, ub128, no spec decode) | After (this config) |
|--------|---------------------------------------------|---------------------|
| Token generation (e2e) | ~80 t/s ceiling | **100–114 t/s** (137 on repetitive content) |
| Prompt processing | ~940 t/s | **2100 t/s @32K / 1590 t/s @100K** |
| 2 concurrent (np2) | n/a | 138–144 t/s aggregate |
| Context | 256K | 256K + 2 slots (11.6 GB/card) |
| Speculative decoding | none | **MTP n=3** (+19% TG) |
| Vision | broken/OOM | **working** (TTFT 2.8–12.3 s by image size) |

Companion data: the full measured matrix (~45 configs) is in [`2026-08-27-qwen3.6-35b-a3b-dual-3060-optimization.csv`](2026-08-27-qwen3.6-35b-a3b-dual-3060-optimization.csv). Sister report: [the same model on a *single* 3060](2026-06-30-qwen3.6-35b-a3b-mtp-single-3060.md) — opposite VRAM regime, opposite optimal architecture.

## The final configuration (copy-pasteable)

```bash
# build: cmake -DCMAKE_BUILD_TYPE=Release -DGGML_CUDA=ON \
#          -DCMAKE_CUDA_ARCHITECTURES=86 -DGGML_CUDA_FA_ALL_QUANTS=ON
# (gcc-12 host toolchain; CUDA 12.0 rejects gcc-13)

llama-server \
  -m Qwen3.6-35B-A3B-UD-IQ4_XS.gguf \        # from unsloth/Qwen3.6-35B-A3B-MTP-GGUF (MTP heads embedded, 18.21 GB)
  --mmproj mmproj-F16.gguf \                  # vision encoder, CPU-resident (see below)
  --no-mmproj-offload --image-max-tokens 1024 \
  -c 262144 --parallel 2 \
  --split-mode tensor --tensor-split 50,50 \
  -ctk q8_0 -ctv q4_0 -b 2048 -ub 1024 \
  --flash-attn on \
  --spec-type draft-mtp --spec-draft-n-max 3 \
  --jinja --metrics --cache-prompt --cache-ram 2048
```

If your three GPUs enumerate differently, select the two 3060s explicitly (`CUDA_VISIBLE_DEVICES=...`; note CUDA's default device ordering is *fastest-first*, which is a heuristic — verify with `ggml_cuda_init` after driver changes, or set `CUDA_DEVICE_ORDER=PCI_BUS_ID`).

## The optimization journey (each step measured)

| # | Change | Effect |
|---|--------|--------|
| 1 | `GGML_CUDA_FA_ALL_QUANTS=ON` build flag | **Mandatory.** Without it, mixed q8/q4 KV cache makes flash-attention PP collapse to ~38 t/s; with it ~2000 t/s sustained |
| 2 | `--ubatch-size 128 → 1024` | PP 940 → 2154 t/s (2.3×) — **the single biggest win** in this project |
| 3 | layer → tensor split | TG 80 → 96 t/s (+20%) at only −3% PP. Opposite of published dense-27B dual-GPU results — MoE tensor mode works well here |
| 4 | explicit `--tensor-split 50,50` | +3–5 t/s over the implicit equal default |
| 5 | MTP (dedicated GGUF, n-max 3) | TG 94 → 100–114 t/s e2e |
| 6 | vision: `--no-mmproj-offload` + `--image-max-tokens 1024` | 4K image TTFT 117–131 s → 12.3 s, with full OCR accuracy |

## Findings worth knowing

**MTP needs the dedicated GGUF.** The plain `unsloth/Qwen3.6-35B-A3B-GGUF` contains no MTP layers ("model doesn't contain MTP layers"). The `-MTP-GGUF` repo variant embeds them (+0.5 GB, same quant ladder) and is drop-in. n-max sweep (e2e t/s): n=1: 111, n=2: 107, **n=3: 112**, n=4: 93. `--spec-draft-p-min`: 0.2 marginally best for chat/code, 0.0 best for reasoning, ≥0.4 clearly harmful (−30%).

**Acceptance-rate caveat.** We report acceptance as `spec_decode_num_accepted_tokens_total / spec_decode_num_draft_tokens_total` from `/metrics` — *per drafted token*, whole-run aggregate. Measured: ~55% (chat, 256K/np2/n=3), 61% (mixed fixture, n=3). If you see 91–95% quoted for the same model family (our single-3060 study), that was **n=2**: higher n-max drafts more tokens that get discarded per miss, mechanically lowering the ratio even at equal per-step efficiency. Don't compare across n-max without the caveat.

**Q4_K_M is *faster* than IQ4_XS here** (chat 109 vs 92, code 120 vs 115 t/s) — K-quant MoE kernels beat the packed IQ4 on this hardware — and it's a higher-fidelity quantization. **But** with MTP draft buffers it only fits ~64K context at np2 (11.95 GB/card, 96K OOMs). If 256K context matters, IQ4_XS is the choice; if ≤64K, Q4_K_M is faster and better.

**Build bug — unequal tensor splits on `925e1179`.** `--tensor-split 45,55` (or `0.54,0.46`) misallocates ~the entire model onto one GPU → cudaMalloc OOM. Verified with both syntaxes; build-specific, not syntax. Explicit `50,50` is required on this commit; upstream documents unequal splits generically, so re-test after any upgrade. (`llama-bench` misapplies `-ts` in layer mode on the same commit.)

**KV quant:** q4/q4 ≈ q8/q4 in throughput everywhere we measured; keep q8_0 keys for fidelity.

**Context scaling (winning config, 1 slot):** TG 86 t/s empty-ctx → 62 after filling ~104K; PP 2096 → 1588 t/s (32K→256K). 256K + np2 fits at 11.56 GB/card.

**PCIe asymmetry doesn't matter.** Our links ran gen4 x4 (6.4 GB/s ceiling) and x8 (13.6 GB/s) — tensor-mode cross-GPU reduction still won by +20% TG despite the asymmetric, modest links.

**Vision, the ugly parts.** GPU-offloaded mmproj **segfaults on any vision request in tensor mode** (and runs at CPU-identical speed in layer mode — not actually accelerated in this build) and doesn't fit at 256K/np2 anyway. CPU-resident is the only option: F16 beats BF16 by ~8% on Zen 3 (no native BF16). The real cost is *token count*: uncapped image encoding is 38–43 s (1080p) and 117–131 s (4K) to TTFT; `--image-max-tokens 1024` caps it ~10× with verified full OCR accuracy (read exact rendered/invoice text at 1024; at 512 it misread fine print — 1024 is the accuracy floor for grounding-style tasks; 512 = fast/coarse). Text generation speed is unaffected by vision requests.

**Rejected, measured:** ngram speculative decoding (no gain simple, −10% with cache); the CPU-expert-cache architecture (thecodacus fork `perf` @ d927e7dc: no-cache 253 pp / 26 tg, best cache config 46.4 tg, vs 96 tg fully-resident — **the cache is for boxes where the model doesn't fit in VRAM**; on a machine where 24 GB holds everything, CPU expert execution is pure loss); fork vs mainline otherwise ≈ equal (mainline preferred: maintainability, and tensor+MTP hits an assert in the fork's meta backend).

## Upgrade methodology (treat the stack as a release)

1. **Pin** commit, model SHA-256s, CUDA toolkit, driver, cmake flags, and the exact systemd unit (we keep a pinning manifest next to the service).
2. **Regression fixture:** 5 fixed requests (2K chat, 12K code, 64K doc, 200K doc, 2×8K concurrent) → record prompt/completion token counts, wall times, MTP acceptance, **output sha256** (temp 0), VRAM end-state. After the build/driver change, all hashes must match the baseline and timings stay in tolerance. We verified the live server is run-to-run deterministic (3 consecutive runs, all hashes identical) — a hash drift after an *upgrade* is a signal, not noise.
3. **Watch** (server `/metrics` with `--metrics` on): MTP acceptance over time (sudden collapse is an actionable alert), TG/TTFT per request, np2 utilization, prefix-cache hit rate, per-GPU VRAM/imbalance, CUDA/OOM errors.

## What this means

A 35B MoE at 256K context, 2 slots, with vision, on two ~$200 cards: ~100–114 t/s decode, ~2100 t/s prefill, ~260 W of GPU TDP max. The two biggest wins were not exotic — a build flag (`FA_ALL_QUANTS`) and a flag we'd left at a 10-year-old default (`--ubatch-size 1024`). The exotic parts (MTP GGUF, tensor vs layer, vision token capping) added another ~25–40%.
