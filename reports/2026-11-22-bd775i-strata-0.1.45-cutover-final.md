# Strata 0.1.45 goes to production on the 48 GB node: quality battery, corrected ablation, verified rollback (final campaign record)

This report closes the three-way campaign opened by the 2026-11-21 report
(B: v0.1.45 passed the pre-registered speed bar; C: HotRod failed at long
context). It covers the three remaining gates in the order they were
executed: the quality battery, the corrected H-ablation, and the controlled
cutover with a verified rollback and an armed 24 h production probation.
The production lane on the 48 GB / 12 GB node (RTX 3060, single-channel
DDR5) now runs **v0.1.45**.

## Gate 1 — the quality battery (paired, 80 probes)

A private 80-probe battery: 50 verifiable-math questions (arithmetic,
algebra, word problems; answer on a final `ANSWER: <number>` line) and 30
Python-function tasks (the model must return a fenced function; a local
runner executes it against hidden test cases, all must pass). Both arms
answered the identical 80 prompts, temperature 0, on the production serve
shape (fresh process, 32 GiB pin, MTP drafter), paired by probe. Every
disagreement was inspected individually.

| | A: v0.1.41 (was in production) | B: v0.1.45 (promoted) |
|---|---|---|
| math (50) | 47 | 47 |
| code (30) | 27 | 27 |
| total | **74 / 80** | **74 / 80** |

The two shared math failures are genuine model errors at this quant
(one off-by-one in a digit-sum chain, one digit-multiple sum); both arms
make exactly the same two. The four single-sided disagreements were all
inspected and none is a systematic version difference:

- two of them are **thinking-budget exhaustion**: the model is a thinking
  model, and on two probes each arm's thinking consumed the 1024-token
  budget before it wrote the final answer, so the serve layer returned an
  empty message. Each arm exhausted its budget on *different* probes — a
  mirror pair, not a regression direction.
- one is truncated code (a function body cut off mid-line → syntax error)
  in the 0.1.41 answer on a narcissistic-number task; 0.1.45 passed it.
- one is a one-shot code variance: on an anagram task the 0.1.45 answer
  passed 2 of 4 hidden tests, 0.1.41 passed all 4.

Two of the probes themselves had authoring errors (wrong expected values),
found by running the battery's own reference solutions through the grader;
the fixed set is what is reported here. **Verdict: no material quality
regression.** Caveats, stated plainly: n=1 per probe, greedy decoding is
not bit-reproducible on this box even for the same binary (established in
the 2026-11-18 work), and a thinking model occasionally out-runs a fixed
token budget. The battery detects regressions at the level of "systematically
wronger", not at the level of "different on this one of 80".

## Gate 2 — the corrected H-ablation

The interim report's ablation run was invalidated (its "off" env vars were
already the defaults), and its attribution reading was withdrawn. The
corrected run settled the question a different way: by reading the fork's
route-resident configuration code (`src/core/verify.cpp`), the stand-in
machinery is **off by default** — the replacement margin defaults to 0
(the missed-pick budget is 0 = off, the fragile re-check is opt-in since
9 Nov, the maximum-stand-in mode is a separate opt-in flag) — and the
production unit sets none of these variables. The deployed engine, in
either version, runs exact routing by default.

Measured at 128K / 200K (fresh process per cell, same production shape):

| mode (all v0.1.45, 256-out cells) | 128K total (s) | 200K total (s) | vs default |
|---|---|---|---|
| default (= exact; in production) | ~146 (derived: W2 primary prefill + 256/29.1) | ~231 (derived: W2 primary prefill + 256/27.9) | — |
| `STRATA_FRAGILE_RECHECK=1` (correctness re-check on) | 147.8 | 229.5 | +1.2% / −0.7% |
| `STRATA_STANDIN=1` (maximum approximation) | 151.1 | 230.6 | +3.5% / −0.2% |

Two findings:

1. **The fork's approximation machinery is inert on this model.** Turning
   the maximum-stand-in mode on buys no speed here (within the run-to-run
   band) and its quality spot (5 easy math probes) matches the default
   (4/5, the one failure being the same known model error the production
   version also makes). The HotRod deficit of the 11-21 report is
   therefore *not* the cost of approximation — the fork's long-context
   loss is in its engine structure on this node, which the corrected
   reading now states with evidence instead of the withdrawn hypothesis.
2. **The safety re-check costs nothing measurable on this machine** (both
   deltas inside the run-to-run band), unlike the ~30% the fork's own
   notes record on their slower node. If
   the owner ever wants the extra correctness machinery in production,
   the cost here is negligible.

Token-level agreement between v0.1.41 and v0.1.45 was also measured (three
prompt lengths, 200 tokens, temperature 0): the texts diverge within the
first 0–115 characters, i.e. from essentially the first token. This
*cannot* be attributed to the version's routing — the same binary
re-run does not reproduce itself on this box either (11-18) — and the
divergent answers were semantically equivalent summaries of the same
passage. It is recorded so that "bit-identical output across versions" is
not claimed anywhere downstream.

## Gate 3 — cutover, verified rollback, probation

The production service is a small out-of-store serve layer whose config
caries the engine path in one field (`exe` in the solo config JSON); the
nix system closure is untouched. The cutover therefore was: replace the
0.1.41 store path with the 0.1.45 store path in that one field and restart
the unit. Before promoting, the full cycle was exercised end to end:
0.1.41 → 0.1.45 → 0.1.41 → 0.1.45, with a verification suite after each
step (models endpoint, basic generation, two-turn KV-reuse check, a 128K
long-context request). Each direction returned to a healthy service in
~60 s (warm page cache). The 0.1.41 generation stays in the nix store
(kept alive by the unit's own path closure) and a timestamped backup of
the config is held alongside the campaign records, so rollback is a
restored file plus one restart — measured, not described.

Two production-behavior facts from the cutover verification, worth keeping:
the 0.1.45 engine cold-prefills 131K tokens at ~940 tok/s and decodes at
31 t/s (matching the campaign matrix), and a repeated identical 128K
request served in ~33 s total — the KV-resident pool is reusing the
previous request's cache as designed. One quirk: a 128K request whose
thinking runs past the token budget returns an empty message from the
serve layer; this was reproduced identically on 0.1.41, so it is a
model/serve property, not a regression.

**Probation (armed at cutover):** a monitor runs every 5 minutes — health
endpoint plus a 128-token canary generation; three consecutive failures
trigger a one-shot automatic rollback to the backed-up 0.1.41 config with
a post-rollback re-verification, after which the monitor keeps logging.
The 24 h window starts at the cutover; the trigger list is the review's
(crashes, persistent hangs/timeouts, OOM, repeated service failures,
serious correctness problems — the canary covers the last one). The
outcome is recorded in the estate's private campaign log; if the window
closes with no rollback event, the probation passes by its trigger
definition and the promotion stands.

  this model, and v0.1.45 already clears the bar.

## Limitations

Single-client (the lane is a solo service), 48 GB regime, one 12 GB card;
the 96 GB re-test may shift the balance (per the 11-19 series). The
quality battery is a one-shot-per-probe smoke gate, not an equivalence
proof. All raw per-run records (cells, responses, grader output,
monitoring log) live in the estate's private repository; a sanitized
extract is available on request.
