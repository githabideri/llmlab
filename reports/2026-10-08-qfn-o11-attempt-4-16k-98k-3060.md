# 2026-10-08 QFN OptLlama attempt-4: the N=36 pin, the 16K/98K matrix, and MTP's real size at depth

**Date:** 2026-10-08 (run windows 2026-10-07 21:05–23:56 UTC and 2026-10-08 06:15–09:06 UTC)
**Category:** Experiment / benchmark
**Hardware:** backup / inference box — Intel i3-9100 (4C/4T, DDR4-2400 2-channel ≈ 38 GB/s), single RTX 3060 12 GB, 46.8 GB host RAM, **no swap**, NVMe. Container with a **42 GiB *hard* cgroup memory limit** throughout (single automatic backstop; the 6 GiB host-available line was log-only advisory).
**Model:** Qwen3.8-Flash-Next, `GSQ-RCO-IQ2_XS` (36.4 GiB expert/dense shard + 26.8 GiB PLE/n-gram shard) + `mtp-Qwen3.8-Flash-Next-Q8_0` (2.6 GiB). The [10-05](2026-10-05-optllama-moe-cache-qfn-single-3060.md) and [10-07](2026-10-07-qfn-o11-ple-page-faults-single-3060.md) reports are the direct predecessors; this is the final OptLlama attempt on this box.

**Builds** (fork `GenerelSchwerz/llama.cpp`): **925933801** — the O11 owner-verified commit; **167742d** — the MTP control (returned HTTP 500 in the 10-05 O7, retested here); **ea2df357** — the N=36 target revision (32,768-element expert cache).

**TL;DR**

- **The 10-05 `N=32` pin does not boot on this box** — the cache allocator rejects `32` at startup. The matrix therefore pins **N=36** (the only other 4-multiple below the 44 accepted at boot), held fixed across all arms. N=36 is ~108 MiB more VRAM than 32 and the 42 GiB cgroup never approached its guard (peak 39.8–39.9 GiB, abort rule 40.5 — never fired).
- **The 16K ladder (3 scored reps per arm, canaries pass):** no-MTP 9.56 → +27% pin 9.97 → +MTP 10.54 (925933801) / **10.28** (167742d, 4.1% below — the MTP fix is a *performance-wash* build choice, not a regime change) → +overlap 10.67 → +overlap +no-think 10.39 (noise). **MTP at 16K is +4–8%, not the 2× predicted by the Codacus/owner references** (their boxes have 6–12 cores; the draft pass is a serial step on 4 cores).
- **MTP acceptance on this box is 0.34–0.66 per rep at 16K (M3: 0.34/0.47/0.58/0.61/0.64/0.66; mean acceptance length 1.7–2.3)** vs the 2.4–3.2 per pass the reference boxes post — the CPU draft is the rate limiter, not the GPU verify.
- **98K (the regime 10-05/10-07 characterized):** MTP **7.40 / 7.53 / 7.57** (median 7.53, 3 scored reps) vs **no-MTP 6.50 / 6.22** (median 6.36, same window) → **MTP at depth is +18.5%**, the same 10–20% class, *not* a doubling. The no-MTP ≥10 t/s prediction at ~90K is **refuted** again (every no-MTP run on this box, 10-05 through this one, lands 6.0–6.5). 98K cold prefill stays I/O-dominated: 832–892 s (110–118 t/s) in the a3 window; the fresh window's warm-start TTFTs are 576–675 s.
- **The PLE-residency lever is closed (rejected by the operator before the run — "the PLE will not go on RAM"):** the direct-row-reader variant (a3) is *slower* on deep prefill than PLE-on (697.8/691.8 s vs 656.6/617.6 s) — the 27–42 MB/s fault rate identified in [10-07](2026-10-07-qfn-o11-ple-page-faults-single-3060.md) dominates both paths; how you touch the table does not beat its bandwidth wall.
- **Safety:** one production stop/restore pair per window (the box's 35B always-on service; stop 06:15:18Z, restore 09:06:47Z, unit file mtime untouched, live-verified at 36.5 t/s with 41/42 MTP drafts accepted post-restore); model shards read-only (SHA-256 before/after); no hardware changes; the 3060/46 GB box is the *floor* of the machine class these numbers describe.

**Conclusion**

The OptLlama lineage on this box ends at **~10.5–10.7 t/s at 16K and ~7.5 at 98K** (MTP on), with the pin choice (36), overlap, and build revision all inside ±5%. The [10-05 "128 GB purchase"](2026-10-05-optllama-moe-cache-qfn-single-3060.md) correction stands and is now re-confirmed from the other side: **cores × PCIe generation, not RAM, is the axis** — the same quant on a 6+ core / newer-PCIe machine posts 18–40 t/s with the *same* 12 GB card. 20–30 t/s on this box remains out of reach for every tested engine; the production 35B service (6.1–6.2× faster, [10-05](2026-10-05-optllama-moe-cache-qfn-single-3060.md)) was untouched and stays. GPU power per phase was not captured in this window (sampler recorded VRAM/util only) — recorded as a gap, not estimated.
