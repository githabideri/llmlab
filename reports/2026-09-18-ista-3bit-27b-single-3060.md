# Qwen3.8-27B 3-bit (ISTA GSQ-RCO) on the single-3060 boxes — MTP, the D-CFR patch, and the 64K/98K ceilings

**Date:** 2026-09-18 (deployment postscripts 2026-09-19/20)
**Category:** Experiment / benchmark
**Boxes:** two single-RTX-3060-12 GB boxes, identical setup on both:

- **Backup/inference box** — Intel i3-9100 (4C/4T), single RTX 3060 12 GB, 40 GB LXC soft limit, Ubuntu 24.04, CUDA 13.1
- **Secondary GPU server** — Intel i5-7400 (4C/4T), single RTX 3060 12 GB (LXC), 20 GB LXC limit (shared with document-AI workloads; ~4 GB free during the campaign), same OS/CUDA

**Model:** Qwen3.8-27B — dense ~27.3B, hybrid SSM + full attention (17 of 66 layers), **native MTP head**. Quant: ISTA DASLab's [GSQ-RCO GGUF release](https://huggingface.co/ISTA-DASLab/Qwen3.8-27B-GSQ-RCO-GGUF) — **IQ3_XXS (3.02 bpw)**, the 2-bit **IQ2_S** sibling, and their `-mtp` variants.
**Engines:** llama.cpp `925e1179` (the boxes' production build) and a 925-based build carrying the **D-CFR** patch — [GDN transactional replay](https://github.com/kadenball/qwen38-27b-rtx3060-dcfr), which removes the MTP draft's redundant GDN recurrent-state copies. The backup-box D-CFR build was compiled from a sha-verified copy of the secondary box's source tree (476/476 steps), so the two boxes ran byte-identical engines.

**TL;DR**

- **3-bit + MTP: 48K on the production build, 64K on the D-CFR build.** 64K is the hard MTP ceiling — 67K and up first-token-OOMs in every batch/n-max/KV variant tested.
- **3-bit without MTP: 98K on the production build** (15.8–19.8 t/s). 100K is 4K tokens over the cliff; 98K is the ceiling.
- **2-bit is genuinely worse**: identical-config 5-item quality battery — 3-bit passes all five, 2-bit fails the code item (broken in-place merge) and the fact-check (wrong top-3 lakes). Not a sampling artifact. The 2-bit model was retired from the rosters.
- **Sampling was wrong in production**: everything ran llama.cpp defaults (1.0 / 0.95 / 0.05 / 0.0) = Qwen *thinking-mode* values. The new sections use ISTA's instruct recommendation (0.7 / 0.80 / 20 / 1.5). Side effect: MTP acceptance drops 84% → 60% — accepted trade.

**Community context for this exact card:** people were running this 27B at 96K with 4-bit KV + small batches + FFN offload (~10 t/s) and at 64K with the D-CFR patch (~30 t/s); 16 GB cards went to 112–131K with `q5_1/q4_0` KV + ngram. The 4-bit-KV `kvarn4` format those threads used is fork-side (BeeLlama / patched builds), not in stock llama.cpp master. Our campaign measured where the *real* ceilings sit on 12 GB, what the D-CFR patch buys, and the sampling/quality consequences.

## Method

Manual `llama-server` invocations on a scratch port (each box's production router stopped for the window), fixed prompt fixtures, streaming `/v1/chat/completions` timing: prefill = `prompt_ms / prompt_n`, decode = `predicted_ms / predicted_n` — engine-reported token counts, never SSE chunk counts (MTP ships multiple tokens per chunk). MTP acceptance from slot `print_timing` log lines. All cells `--no-warmup --no-cache-idle-slots --fit off`, q4_0/q4_0 KV unless noted; VRAM from 1 Hz `nvidia-smi` polling (which also gates each cell: wait for the GPU to actually free before the next boot — one 72K cell initially "failed" purely because the previous server's VRAM hadn't drained).

**No energy numbers:** neither 3060 box has a wall-plug meter (unlike the primary GPU server), so this campaign reports no Wh — GPU dmon power was observed, not integrated.

## MTP acceptance × sampling

| Sampling | accept | mean accepted len |
|---|---|---|
| llama.cpp defaults (1.0 / 0.95 / — / 0.0) — what every production section had been running | ~84% | 2.3–2.6 |
| ISTA instruct (0.7 / 0.80 / 20 / 1.5) | 60–63% | 2.2 |

The sampling regime measurably changes draft acceptance (lower temp / narrower top-p → more rejection). Even so, n-max 2 at ISTA sampling gives 25–29 t/s vs 16–20 t/s without MTP — MTP stays on for the 64K service. Note the Qwen3.8 jinja template defaults to *thinking* mode; instruct mode = `chat_template_kwargs: {"enable_thinking": false}` (verified both ways — without it a 512-token budget is consumed entirely by `reasoning_content`, which reads like an "empty reply").

## Quality: 3-bit vs 2-bit (identical config, both boxes)

Five-item battery: arithmetic derivation, in-place merge code, geography fact-check (largest lake / top-3 by area), 16K-document buried fact, vision (red + blue square). Same server config for both quants; ISTA no-think sampling; default (1.0/0.95) no-think sampling produced the same pass/fail pattern.

| Item | 3-bit | 2-bit |
|---|---|---|
| arithmetic (1024) | ✅ full derivation | ✅ |
| in-place merge code | ✅ correct two-pointer code | ❌ broken merge logic |
| lakes fact-check | ✅ Canada 202,080 km²; correct US/Canada/Finland ranking | ❌ claims Russia #1 |
| 16K buried fact | ✅ exact value + doc section | ✅ (2-bit survives this one) |
| vision | ✅ both squares named | ✅ |

The "2-bit is too stupid" feeling was real and quantization-caused, not a sampling artifact.

## What shipped (postscript, 2026-09-19/20)

Per box (both boxes identical):

1. **8080 router** (production 925 build, `--models-max 1`): 35B-MTP resident at boot; a 3-bit 98K no-MTP section (b256/ub128, mmproj on CPU, ISTA instruct sampling).
2. **8090 service** (new unit, D-CFR build): 27B-only, on-demand — the **3-bit 64K MTP model is the user-facing 27B** (25–29 t/s, prefill ~300–425, accept ~60%). **The 35B must never be added to this preset** — D-CFR costs it ~85% prefill.
3. **llama-mux on 8081** (stdlib-Python systemd unit): the single endpoint per card, fronting 8080 + 8090. It lists the roster (35B + 3-bit-64K-MTP) and performs *real* exclusive-GPU switching for a request that names the non-resident model: unload the other backend's model → poll `nvidia-smi` to <500 MiB → load → poll until genuinely loaded → proxy (chunked, SSE-safe). ~30–60 s per direction. Mux v2.2+ is additionally the **telemetry authority** for the 27b: the D-CFR build's per-token metrics counters freeze (only the decode counter moves), so the mux synthesizes `/metrics` from the request-level usage data it injects into every proxied request itself; the 35B path stays a pure passthrough.

Roster changes that followed: the 98K no-MTP model was **parked in a dormant preset file** (off every roster — it was leaking into auto-discovery, its "loads" were optimistic, and one user-triggered load evicted the resident 35B), and the 2-bit model was **retired** per the quality battery (GGUF files kept on disk; either is revivable by re-adding a section). Both boxes end with 35B resident, live-verified. Live-fleet telemetry (llm-hub, 7 days after shipping) corroborates the campaign: the 3-bit 64K-MTP model ran **~24–28 t/s on real agent traffic** on the secondary box; the backup box's average reads lower (15.6 t/s) from sparse traffic — the mux's synthesized counters are a coarse approximation, so the controlled numbers above stay authoritative.

**Ops gotchas from the campaign** (also in the unit notes in [docs/systemd.md](../docs/systemd.md)):

- llama.cpp `--models-preset` **merges all sections into a global base** — a section must explicitly override any key it wants different from its neighbours, or e.g. a 2-bit section's MTP settings leak into a 98K no-MTP load and OOM it. The overrides must stay in place even after the section they were overriding *for* disappears.
- The router **auto-detects MTP from `-mtp` GGUFs** when no `spec-type` is given.
- `POST /models/load` is async (and can hold the response for minutes on a cold 10 GB no-mmap load) — treat it as fire-and-forget and poll `/models` (status is nested: `"status":{"value":"loaded"}`).
- `pkill -x llama-server` (exact comm) only — a pattern pkill matches your own ssh command line.
- In a later **single-mode D-CFR trial** (no router, mux-driven start/stop; abandoned): `--n-gpu-layers 99` must be *explicit* — the D-CFR build's auto-fit picked 54 layers → 2.4 t/s decode; and the 99-layer variant OOMs the MTP draft context on one of the two builds while the other tolerates it. The two D-CFR builds from identical source disagree on KV allocation timing — another reason the routed config (where the preset sizes the MTP context) is the working one.

## What's *not* possible on 12 GB at 3-bit (measured — don't retry)

- 100K+ at any config (98K is the no-MTP ceiling; 100K first-decode OOMs at b256 *and* b128)
- 65K+ with MTP, even on the D-CFR build (67K first-token OOMs in every variant)
- 57K+ with MTP on the production build
- q8_0 K-cache on this model/build (CPU quantization pass → 7.6 t/s prefill, GPU idle); q4_0/q4_0 is the working KV
- the 35B on the D-CFR build (−85% prefill)
- mmproj on GPU at 64K (needs CPU; vision still works, ~26 t/s)

100K at 3-bit would need a bigger card (a 24 GB 3090 has the headroom) or KV offload to system RAM at a speed cost not yet measured (the LXC limits are 20–40 GB).
