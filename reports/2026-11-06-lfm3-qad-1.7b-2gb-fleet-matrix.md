# LFM3-1.7B QAD across the fleet's small cards: decode has no cliff, prefill does

**2026-11-05/06** · experiment / benchmark · fleet matrix: RTX 3060 12 GB (LXC on the secondary GPU server, i5-7400), HP OMEN 15 (GTX 1060 6 GB, i5-7300HQ), and the 4 vCPU Pascal VM (GTX 1050 2 GB + GT 1030 2 GB, same i5-7400 host) · CPU baseline on the Pascal VM's i5-7400 (4 vCPU)

**TL;DR**

- LFM3-1.7B in its QAD-Q4_0 quantization (1.05 GB file, 1.73B params) is the first sub-2 GB model in the fleet that serves a *real* agentic context on a 2 GB Pascal card: weights + 32K KV fit, **64K is the 2 GB ceiling** (KV is 12,288 B/token — measured 4.54 GB total at 256K on the 3060).
- **Decode does not decay with session depth.** tgen-128 on the 3060 is 239.1 t/s at an empty context and 238.5 t/s at a 256K-filled context (Δ < 0.3%). 18 of the 24 layers are short-window (gated conv/SSM) attention, so the per-token KV work barely grows. The "agentic session cliff" people report on dense models is a **prefill** phenomenon here: the 3060's prefill is flat to 32K (≈8.7k t/s) then falls −33% / −51% / −68% at 64K / 128K / 256K.
- The 6 GB Pascal laptop (GTX 1060, 2017) serves it too: prefill 1462 t/s at 1K falling to 188 t/s at 256K, tgen flat at ~73 t/s across 4K–256K — the 256K roof fits with headroom on 6 GB.
- **Pascal deployment caveats (both found the hard way):** the toolkit must be CUDA 12.9 — the last one with `sm_61` (CUDA 13 dropped Pascal) — and **flash-attention must be disabled** (`--flash-attn off`): with this build's default (on) the model loads and then the process deadlocks in a futex, GPU idle, no Xid, driver recovers the VRAM. Also: LFM3 emits *nothing* on a raw prompt (it exits cleanly on the first token) — it needs its chat template, so functional checks must go through a server chat endpoint, not `llama-cli -p`.
- CPU (4-core Kaby Lake, clean CPU-only build): tgen ~19–21 t/s, prefill ~84 t/s at 1K — the QAD dequant has no vectorized CPU path in this build, so prefill is the weak point; decode is still interactive for short sessions.
- Status: the 3060 and 1060 matrices are complete (both LFM3 models, 256K roof on the 3060, 32K roof on Omni). The 1050/1030 VM cells are blocked on hardware: both 2 GB cards are internally dead (a host reboot clears the PCIe-level wedge but not the card state; **only an AC power cycle of the host recovers them**). The VM's production ASR service is paused until the cards are back.

## Goal

Liquid AI's LFM3 family (announced 2026-10-27) ships a 1.7B "QAD" (quasi-arbitrary-precision dequantized) model that quantizes to ~1.05 GB and a 2B omni-modal sibling (text + image in, text + audio out). The question for this fleet: **do the fleet's small cards (2 GB Pascal ×2, 6 GB Pascal, 12 GB Ampere) and 4-core CPUs actually serve this model at useful context, and what does its hybrid-attention architecture do to the classic "session depth" cliff** — the decode slowdown that makes long agentic conversations feel dead on dense models.

Secondary: a public recipe for running *any* current llama.cpp on 2017-era Pascal in 2026 (CUDA 12.9 + the flag caveats), and a measurement of LFM3-Omni-2B on the same cards (it has a 32K context roof by design).

## Setup

- **Model:** `LFM3-1.7B-QAD-Q4_0.gguf` (1.05 GB; 24 layers, 6 full-attention, 18 short-window) and `LFM3-Omni-2B-Q4_K_M.gguf` (1.02 GB + 0.29 GB mmproj; 32K context roof), both from the vendor's HuggingFace page. QAD is the vendor's dequantization scheme: weights stored in a packed 4-bit-ish form, dequantized in-kernel.
- **Build:** llama.cpp `3de52ac` (0.9.0-dev, 2026-11-04), compiled twice: `CMAKE_CUDA_ARCHITECTURES=86` (3060) and `=61` (both Pascal boxes) with the CUDA 12.9 toolkit. The 12.9 toolkit is **unpacked, not installed** (7 component debs `dpkg -x`'d into one tree; no system-wide CUDA touched) — see Commands.
- **Flags:** `--n-gpu-layers 99 --load-mode none` everywhere (the `load-mode none` form is the 2026-Pascal workaround for the `cublasCreate_v2 = 3` mmap failure documented in [the 2026-09-27 1060 report](2026-09-27-pascal-1060-2026-llama-cpp-35b-128k.md)); on Pascal additionally `--flash-attn off` for any run that generates (see Observations). `llama-bench` runs are template-free by construction and were not affected by the FA deadlock.
- **Protocol:** one model at a time per card; production services on each box stopped (registered), window run, service restored and smoke-checked. Per-depth tgen measured as separate `llama-bench` invocations (`-p N -n 128 -r 3`) because this build's bench has no `-c` flag and a multi-`-p` + single-`-n` run reports only one ambiguous tgen row.

## Commands

The Pascal (sm_61) build — the reusable recipe:

```bash
# 1) unpack CUDA 12.9 (7 debs: nvcc, cublas, cublas-dev, crt, nvvm, cudart-dev, cudart) into $T
# 2) normalize: version file at root; lib symlinks in lib64/ -> targets/x86_64-linux/lib/
# 3) patch $T/include/crt/math_functions.h: sinpi/cospi/sinpif/cospif need noexcept(true)
#    (glibc 2.41 defines them noexcept and the CUDA 12 headers do not — a hard error; CUDA 13 unaffected)
# 4) a CMAKE_PROJECT_INCLUDE that hand-creates the CUDA::cudart imported target (FindCUDAToolkit
#    finds the .so in the targets/ layout but does not emit the target)
cmake -B build-s61 -DCMAKE_CUDA_ARCHITECTURES=61 \
  -DCMAKE_CUDA_COMPILER=$T/bin/nvcc -DCUDAToolkit_ROOT=$T \
  -DCUDA_CUDART=$T/targets/x86_64-linux/lib/libcudart.so \
  -DCUDA_CUDART_LIBRARY=$T/targets/x86_64-linux/lib/libcudart.so \
  -DCMAKE_PROJECT_INCLUDE=zz-cuda-targets.cmake
cmake --build build-s61 -j4
```

Battery (per card; `CUDA_DEVICE_ORDER=PCI_BUS_ID` + `CUDA_VISIBLE_DEVICES` pin the card):

```bash
# prefill ladder
llama-bench -m M.gguf --n-gpu-layers 99 --load-mode none -p 1024,4096,8192,16384,32768,65536,131072 -n 0 -r 2
llama-bench -m M.gguf --n-gpu-layers 99 --load-mode none -p 262144 -n 0 -r 1
# tgen at filled depth
llama-bench -m M.gguf --n-gpu-layers 99 --load-mode none -p <depth> -n 128 -r 3
# functional (template-aware)
llama-server -m M.gguf --n-gpu-layers 99 --load-mode none -c 4096 --flash-attn off --port 8097
curl -s localhost:8097/v1/chat/completions -d '{"model":"m","max_tokens":32,"messages":[{"role":"user","content":"Say OK in one word."}]}'
```

## Observations

### The cliff is in prefill, not decode

3060, 1.7B QAD-Q4_0:

| metric | 1K | 4K | 8K | 16K | 32K | 64K | 128K | 256K |
|---|---|---|---|---|---|---|---|---|
| prefill t/s | 8723 | 8803 | 8555 | 8021 | 7133 | 5862 | 4284 | 2773 |
| tgen-128 t/s (filled) | 239.1 | 239.4 | — | 238.9 | — | 238.9 | 239.0 | 238.5 |

Prefill is flat to ~32K and then falls ⅓ → ⅓ → ⅓ per doubling past that (re-reading history through the 6 full-attention layers, whose KV is the 12,288 B/token monster). Decode is a **flat line** across the entire 0→256K range. For an agentic session this means: the per-turn cost that hurts is the prompt re-read (the prefill of your conversation history), and the token stream the user watches stays at full speed no matter how long the session has run. A dense model of this size would show visible decode decay; this architecture's short-window layers keep per-token KV work nearly constant.

### The 2 GB ceiling

KV at 12,288 B/token: 16K → ~0.2 GB, 64K → ~0.8 GB, 128K → ~1.55 GB, 256K → 3.15 GB (measured 4.54 GB total at 256K on the 3060). Against 2 GB of card: weights 1.05 GB + runtime leave room for ~32–48K of context; 64K is the practical 2 GB ceiling (exact per-context VRAM for the Pascal pair: pending the host reboot — see Status). The 6 GB laptop clears 128K comfortably; 256K fits with headroom [pending 1060 VRAM sweep].

### Pascal: two silent traps

1. **Flash-attention deadlock.** With this build's default FA (on), both LFM3 models load onto the 1060 and then the process parks in a futex (`wait_woken`), GPU at 0%, indefinitely; no Xid is logged and the driver is otherwise healthy (a killed run's 4.5 GB of VRAM was reclaimed within minutes). `--flash-attn off` removes the hang entirely and the models work. (The 3060 build is unaffected — sm_86 runs FA fine.) This is a Pascal-specific execution-path bug in this build generation, worth reporting upstream; it would also explain any "my old card just hangs after loading" reports on current llama.cpp with hybrid-attention models.
2. **Raw prompts produce nothing.** LFM3 exits cleanly (rc 0, empty completion) on any raw prompt — verified on CPU with a healthy box, so it is model/template behavior, not hardware. The vendor's chat template must be applied, which in this build means going through `llama-server`'s chat endpoint (this build's `llama-cli` has no chat-template flag). Any "the model is broken" check on this family must use a templated path.

### CPU is a workable second home

On 4-core Kaby Lake CPU (clean CPU-only build): tgen-128 **19.85 ± 1.29 t/s** with no depth effect to 8K, prefill 84 / 79 / 75 t/s at 1K / 4K / 8K (see the CPU metrics section). The QAD dequantization is not vectorized in this build's CPU path, so prefill is the weak point (~⅓ the 1060's rate); decode is still interactive for short sessions, and a 32K re-read at ~80 t/s takes ~6–7 min, which is where the GPU earns its keep.

## Metrics (measured)

### 3060 (sm_86, build 3de52ac, CUDA 13.2)

1.7B QAD-Q4_0 — the full matrix above (prefill ladder + per-depth tgen, 2–3 reps). VRAM 1.42 GB @16K → 4.54 GB @256K.

Omni-2B Q4_K_M (32K roof): prefill 8242 / 8374 / 7664 / 6852 t/s at 1K/4K/16K/32K (mild slope, no cliff in-range); tgen 223.1 (empty) → 222.6 (32K filled) — flat. Weights 1.02 GB + mmproj 0.29 GB; 32K KV ≈ 0.39 GB. Functional: image probes exact, ASR verbatim (dense speech ≈ 12.7 audio tokens/s, so 32K ctx ≈ 35–40 min of dense audio), TTS 24 kHz WAV, TTS→ASR round-trip verbatim.

### OMEN 1060 (sm_61, build 3de52ac, CUDA 12.9, FA off)

1.7B QAD-Q4_0 (993 MiB weights):

| metric | 1K | 4K | 8K | 16K | 32K | 64K | 128K | 256K |
|---|---|---|---|---|---|---|---|---|
| prefill t/s | 1462 | 1353 | 1229 | 1034 | 785 | 533 | 330 | 188 |
| tgen-128 t/s (filled) | — | 72.8 | — | 73.1 | — | 72.8 | 72.8 | 72.7 |

The same shape as the 3060 at 1/6 the speed: prefill falls ~⅓ per doubling past 32K (128K → 256K is −44%, steeper than the 3060's −35% — the 60 W TGP cap starts to bite), decode is flat to the 256K roof. Power: wall sampling at 10 s resolution shows the card pegged at its 61.5 W TGP during prefill phases.

Omni-2B Q4_K_M (32K roof): prefill 1332 → 733 t/s across 1K–32K; tgen-128 63 t/s, flat from empty to 32K filled. 1.24 GB VRAM at 32K+2K output.

### CPU (i5-7400, 4 vCPU; CPU-only build of the same source, ngl 0, 4 threads)

1.7B QAD-Q4_0: tgen-128 **19.85 ± 1.29 t/s** (no depth effect to 8K); prefill 84.0 / 79.1 / 74.8 t/s at 1K / 4K / 8K — nearly flat, mirroring the GPU prefill shape at ⅓ the rate. Omni-2B: tgen-128 18.96 ± 0.88; prefill 92.5 / 90.3 / 84.5 t/s. These numbers come from a `GGML_CUDA=OFF` build: with the CUDA-compiled binary run where the driver is half-dead, ggml's backend init fails mid-way and prefill degrades another ~10× while tgen looks normal — a trap for anyone reading CPU numbers off a CUDA build on a broken GPU. (The fleet's other 4-core Pascal-era CPU point, recorded on the OMEN laptop, is not directly comparable: that run happened with the laptop's 1060 present and its VRAM partially occupied, so its prefill figure is a hybrid, not a clean CPU baseline.)

## Energy

10 s-resolved wall-power sampling on the OMEN during the 1060 battery (`power.draw`): the card pegs its **61.5 W TGP** during prefill phases and sits at ~35–40 W during decode; the wall envelope stays under the laptop's 90 W AC. The 60 W cap is the binding constraint: the 256K prefill (188 t/s) runs hotter and slower-per-byte than the 3060's equivalent (2773 t/s, no cap near). The 3060 windows were not power-sampled (no meter on that path); the Pascal VM has no wall meter either.

## Status and open cells

- **Complete:** 3060 (1.7B full ladder incl. 256K, Omni full; the production 35B brain restored and smoke-checked after each window); OMEN 1060 (1.7B to 256K, Omni to 32K; its production 35B service restored after the window); CPU cell on the Pascal VM (clean CPU-only build).
- **Blocked on an AC power cycle:** the Pascal VM's 1050/1030 cells. The two 2 GB cards entered a stuck state during the window (QEMU starts of the VM exit immediately; the GT 1030 does not even accept a driver bind). A reboot of the i5-7400 host on 2026-11-06 cleared the *PCIe-level* wedge (the cards re-bind to vfio, the VM boots, the driver loads) but **not the card-internal state**: `nvidia-smi` finds no device and `cudaGetDeviceCount()` fails in the guest, PCI function reset returns `ENOTTY`, and a secondary-bus reset on the 1050's root port (its bus carries only that card pair, so it is a safe, narrow operation) completes in the kernel log without healing the card. On this hardware generation the only recovery is full loss of power to the board. The 1030 was removed from the VM's passthrough config so the VM can start at all; the 1050 remains assigned, and everything needed for the GPU cells (sm_61 build, models, battery script with the pmon/sidecar fixes) is staged on the VM.
- **Also found during the VM recovery (documented because it is a trap for anyone with a "never-restarted" VM):** the VM's root filesystem would not cold-boot — its primary ext4 superblock had been zeroed at provisioning time (every image of it since shows the same wipe), and six weeks of continuous uptime had hidden it. It boots again via the surviving alternate superblocks, and the primary was reconstructed on 2026-11-06 (the full forensics live in the private estate repo; the one-line takeaway: a superblock wipe that hits only the 1K-mirror slot looks like "middle fields corrupt" when you decode the 4K-layout copy, and the GD table after the primary is part of the same wiped region). The VM's production ASR service is paused until the cards return; a daily audio-pruner (14 d retention / 4 GB cap, transcripts kept) is installed so the 38 GB rootfs cannot repeat its 2026-10-11 full-disk failure.
- **Not tested:** the QAD model's agentic/tool-call behavior at depth (tool calls and JSON-via-prompt verified at small context on the 3060; the vendor's `/nothink` switch is not honored by the GGUF template — the server `--reasoning off` flag is the working switch).

## Conclusion

LFM3-1.7B QAD is the first model in this fleet's 2 GB class where the *hybrid architecture* decides the deployment story: decode speed is independent of session depth (flat 239 t/s to a 256K context on the 3060), so the model stays responsive for as long as the KV pool lasts, and the only depth cost is the one-shot prefill of history (which cliffs past ~32K, like any long-context attention). For the 2 GB Pascal pair the practical envelope is ~32–64K context at interactive decode; the 6 GB laptop gets the full 128–256K range. On Pascal, 2026-era llama.cpp needs the 12.9 toolkit and FA off, and the family's chat template must be applied server-side or the model looks dead.
